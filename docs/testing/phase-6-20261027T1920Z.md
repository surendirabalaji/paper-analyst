## 4. Defects

### P6-D1: S2 Major, **phase-blocking**: the SQL guard does not bound memory

- **Input** (local, real DB): `run_readonly(DB, "WITH RECURSIVE r(s,n) AS (SELECT 'xxxxxxxx',0 UNION ALL SELECT s||s,n+1 FROM r WHERE n<25) SELECT max(length(s)) AS n FROM r")`.
- **Observed:** accepted. It built a 268,435,456-character string in 1.19 s, and the process peaked at **2.14 GB RSS** (`/usr/bin/time -l`). With `n<24`: 134 MB string, 1.38 GB RSS, 0.56 s. A single `printf('%200000000s','x')` call (one VM op) added 200 MB. `replace(...)` nesting reaches SQLite's 1e9-byte default limit.
- **Reachability:** deployed case F-mem. The Data agent ran a user-supplied `printf` query verbatim (scaled down to 3 MB on purpose; I did not run a large version against the shared service).
- **Expected:** a bound on value and result size, so that an accepted query cannot use more than a small, fixed amount of memory.
- **Likely fix:** in `connect_ro` or `run_readonly`, set `con.setlimit(sqlite3.SQLITE_LIMIT_LENGTH, ~1_000_000)` (Python 3.11+). Treat the resulting "string or blob too big" as `sql_rejected` or `sql_timeout`, not as a crash. Optionally also set `SQLITE_LIMIT_SQL_LENGTH` and drop `printf`/`format` from the allowlist, or cap the width.
- **Rubric impact:** Deployment and scalability (one public request can OOM an instance that serves up to 10 concurrent requests), and the bounded-execution requirement for generated queries.
- **Regression tests:** `tests/unit/test_phase6_tester.py::test_T6_SQL_MEM_*` (sizes 20–64 MB, safe to run).

### P6-D2: S3 Minor: rows without `arxiv_id` are reported as "found no matching papers"

- **Input** (MOCKED, `test_T6_NOPAPERS_…`): the Data task runs `SELECT title, published FROM papers WHERE year = 2025 ORDER BY published DESC LIMIT 2`, which returns 2 rows, and a Summary task depends on it.
- **Observed:** `found_no_papers` checks only `paper_ids`, so the Summary task is skipped with `no_upstream_papers`, the request status stays `done`, and the synthesizer is told "(not run: the database lookup found no matching papers…)". That contradicts the D1 rows it receives.
- **Expected:** the skip applies only when Data's successful queries returned 0 rows. If rows lacked ids, either hand off what is known (titles), or mark the dependency partial with a truthful note.
- **Likelihood:** low. The prompt asks for `arxiv_id`, and all 11 deployed Data queries included it.
- **Component:** `app/graph.py` (`found_no_papers` and the synthesize note), `app/agents/data.py` (`paper_ids`).
