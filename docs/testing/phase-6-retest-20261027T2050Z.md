## 4. Defects

### P6-D1 (reopened): S2 Major, **phase-blocking**: the SQL guard still does not bound memory

**P6-D1a, wide rows**

- **Input:** `run_readonly(DB, "WITH a(s) AS (SELECT replace(replace(replace(replace(replace('x','x','xxxxxxxxxx'),'x','xxxxxxxxxx'),'x','xxxxxxxxxx'),'x','xxxxxxxxxx'),'x','xxxxxxxxx')) SELECT s,s,…(400×) FROM a, papers")`.
- **Expected:** the query is refused, or peak memory stays at a small fixed amount.
- **Observed:** accepted. 1,996 MB peak RSS in 0.26 s. The cost is about columns × value size × 51 rows, and the SQL limit allows about 900 columns. On the deployment, the same shape was executed verbatim by the Data agent.
- **Cause:** each value is capped at 100 KB, but there is no cap on the number of columns or on the total size of a row or result, and `fetchmany` loads the rows before `_cell` cuts them.
- **Possible fixes (the developer chooses):**
  - set `SQLITE_LIMIT_COLUMN` low (for example 32–64);
  - lower `MAX_VALUE_BYTES` (cells are cut at 300 characters anyway);
  - fetch row by row with a running total-bytes budget.

**P6-D1b, temp-file spill**

- **Input:** `WITH RECURSIVE r(n) AS (SELECT 1 UNION ALL SELECT n+1 FROM r WHERE n<1000000) SELECT s FROM (SELECT replace(<10,000-char>,'x','xxxxx')||n AS s FROM r) GROUP BY s ORDER BY s DESC`.
- **Expected:** a bounded refusal or timeout, with little temp space used.
- **Observed:** about 946 MB of temp files in 0.49 s. With unlimited space the query runs for the full 2 s, so several GB are likely. The connection's `mode=ro` and `query_only` settings do not limit temp files. On Cloud Run they are stored in instance memory, so a 2 GiB instance can be killed for running out of memory.
- **Possible fixes:**
  - keep temp storage in the heap (`PRAGMA temp_store=MEMORY`) and cap it (`PRAGMA hard_heap_limit`, which applies to the whole process; check how it interacts with other SQLite users);
  - or run the query in a child process with `RLIMIT_AS`/`RLIMIT_FSIZE`;
  - or make the value and op caps small enough that the most data a query can produce in total is bounded.
- **Rubric impact (both):** Deployment and scalability, and the bounded-execution requirement for generated queries. One public request can crash an instance that serves up to 10 concurrent users.
- **Regression tests:** `tests/unit/test_phase6_tester_retest.py`. They are sized so that a failing run stays under about 300 MB, and the spill test runs in a subprocess with a file-size limit.
