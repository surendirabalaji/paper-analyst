## 4. Defects

**P7-D1 (Minor, non-blocking).** A corrupt `papers.db` is blamed on the model's query.

- **Steps:** `run_readonly(<file of junk bytes>, "SELECT count(*) FROM papers")`.
- **Expected:** `sql_unavailable` (service side), as for a missing database.
- **Observed:** `sql_error` "file is not a database". In the graph (T7-S3), the Data agent spends its repair round. The task ends as `invalid_sql`, and the answer says the agent "wrote a database query that was still invalid … Try rephrasing it".
- **Location:** `app/sqlguard.py` `_execute`. The `"not a database"` branch deliberately keeps `sql_error`.
- **Rubric impact:** small. It is an honesty and diagnostics gap for the "corrupt asset" injection, and the deployed database is baked into the image.
- **Tests:** `test_T7_S2`, `test_T7_S3` (strict xfail).

## 5. Non-blocking notes

- **P7-N1 (polish).** Faults in `hang` mode lose the injected label once the real timeout fires.
  - The `error` events have `injected: null`.
  - When the planner hangs (L2), the answer says "This looks temporary … Please try again in a moment" with no injected label.
  - The meta row and `fault_injected` events are still shown, and `worker_result` does carry `injected: true` (D4).
  - The developer's own test `test_hung_planner_keeps_the_synthesis_reserve` encodes this behaviour.
- **P7-N2 (Phase 8).** After a non-OK HTTP response such as 403, the turn still shows "Planning…" above the error. The loading text does not settle.
- **P7-N3 (polish, security hygiene).** `#fault_token=` stays in `location.hash`, where it is visible in the address bar and browser history. Suggestion: call `history.replaceState` after reading it. A crafted link with a wrong token only makes that browser's own requests return 403, so it cannot be used to inject faults.
- **P7-N4 (polish).** The 422 detail echoes the whole spec, up to about 6 KB. Only token holders can reach this response.
- **P7-N5 (polish).** The `deploy.sh` grep does not catch `FAULT_INJECT = x` with spaces around `=`. `python-dotenv` would read that line, but `env_to_yaml`'s allowlist still blocks it, so nothing is deployed. The grep also refuses `FAULT_INJECT=""`, which is harmless.
- **P7-N6 (polish).** The planner `error` event has no `error_kind` field. Worker error events do have one.
- **P7-N7 (polish).** With a missing Chroma directory, startup is refused with a cryptic "Read-only file system (os error 30)". An empty directory gives "Collection … does not exist". Both fail safely.
- **Cosmetic items the developer already noted:**
  - The note contains raw Markdown `**`/`---` (P2-N5, Phase 8).
  - The trace error row repeats the injected label.
  - The answer body says "the database retrieval failed" without the injected label, but the note carries it.
- **Latency.** I saw no regression on requests without faults (L6, D5). Two things matter only under faults:
  - A hung planner can use 40 s (20 s plus a 20 s retry) before fallback, which is within the design.
  - The synthesis reserve shortens worker time only when a request is already near 90 s.
